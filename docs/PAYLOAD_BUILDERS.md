# Legacy payload builders (phase 4)

**Status: research builders with fixture-proven byte parity for a subset of payloads. Not a transaction constructor and not consensus.** Output is an ASCII string with no OP_RETURN wrapping, signature, activation, balance, or authority check.

Implementation: [`src/payload_builders.rs`](../src/payload_builders.rs). Tests: unit tests in that file and [`tests/payload_builders.rs`](../tests/payload_builders.rs). Parity vectors: [`fixtures/payload_builder_js_vectors.tsv`](../fixtures/payload_builder_js_vectors.tsv), generated by [`scripts/generate_payload_builder_vectors.mjs`](../scripts/generate_payload_builder_vectors.mjs).

## Source pin

- `patrickdugan/tradelayer.js@dca0888`, `src/txEncoder.js` and `src/txDecoder.js`. The frozen copies in `fixtures/legacy_types_source_txEncoder.txt` and `fixtures/legacy_types_source_txDecoder.txt` have git blob hashes `94201b4e...` and `4728f1bd...`, both verified by the generator.
- `bignumber.js` 9.1.2, the version pinned by the JS `package-lock.json`. The vendored copy is `fixtures/js_vendor/bignumber-9.1.2.js` (sha256 `20db2d8d...`, matching the npm tarball; integrity `sha512-2/mK...` checked against the lockfile).

The generator runs the frozen encoder and decoder in `node:vm` with no other imports and no network. Each row records the JS output for one fixed input, the JS decoder reading of that output, and the outcome the Rust builder must produce. `parity` is `match` only when the Rust outcome is byte-identical to the JS output.

## Payload mapping

The task named "type 0" for simple send. The JS source says otherwise: `encodeSend` writes `tl2`, and the legacy dispatcher maps type 2 to send. The other mappings are confirmed by `encodeIssueOrRevokeAttestation` (`tl9`), `encodeCommit` (`tl4`), and `encodeWithdrawal` (`tl21`).

| Payload | Legacy type | Builder | Parity |
| --- | --- | --- | --- |
| Simple send (direct) | 2 | `build_simple_send` | Byte parity for whole-token amounts; fractional amounts diverge (see below) |
| Attestation | 9 | `build_attestation` | Byte parity for numeric `revoke` 0/1 and the other fields |
| Commit to channel | 4 | `build_commit_to_channel` | Byte parity for the supported shape; several divergences (see below) |
| Withdrawal from channel | 21 | none | Not implemented: JS output is not decodable as written |
| Send all | 2 (`1;<addr>`) | none | Not implemented: the JS direct encoder returns the body without any envelope |

The JS `encodeSend` for send-all returns `1;<address>` with no `tl` prefix, so there is no on-chain payload to match. The `tl21;<addr>` form in the existing audit fixtures is a constructed value, not JS output.

## Results

44 fixture rows: **18 byte-identical to JS**, **26 documented divergences**. Breakdown:

- Simple send (17 rows): 6 match, 11 divergent, including boundary and malformed-input rows.
- Commit to channel (14 rows): 7 match, 5 divergent, 2 unrepresentable. The unrepresentable rows are counted as divergent in the `parity` column.
- Attestation (10 rows): 5 match, 5 divergent.
- Withdrawal (3 rows): no builder, counted as divergent.

The divergent rows are not a failure of parity testing. They document where JS output is wrong or lossy and where this module refuses or emits a different, decodable form.

## Divergences from the JS encoder

Each item lists the JS behaviour, what the legacy decoder does with those bytes, and what the Rust builder does.

1. **Fractional send amounts omit `~`.** `encodeSend` computes `scaledAmt.integerValue()?.toString(36) ?? '0' + '~'`. The `+` binds tighter than `??`, so `'0' + '~'` is the fallback, which runs only when the left side is nullish. The left side is always a string here, so the tilde is never appended. JS `0.5` token becomes `tro8w`, which `decodeAmount` reads as 50,000,000 whole tokens. Rust emits `tro8w~` (atomic units with tilde), which the decoder reads as 0.5 token. Test: `documented_javascript_divergences_as_read_by_decoders`.
2. **One atomic unit.** JS `0.00000001` emits `1`, which decodes as one whole token (100,000,000 atoms). Rust emits `1~`.
3. **Amounts above 2^53-1 atoms.** The JS decoders parse base-36 into a JS Number before applying BigNumber, so values above 2^53-1 lose precision on the chain side. The Rust builders refuse them with `AmountExceedsLegacyPrecision`, and `u64::MAX` is one such refusal. JS emits exact-looking base36 for `u64::MAX` atoms, which the decoder misreads.
4. **String amounts are emitted verbatim.** `encodeSend` calls `amt.toString(36)`, which ignores the radix for strings. JS `'18446744073709551615'` is emitted as decimal text. Rust takes integer atoms and parses text with `parse_atomic_amount`, which rejects floats, negatives, signs, whitespace, and overflow above `u64::MAX`.
5. **Negative and NaN amounts.** JS emits `-1` and `NaN` unchanged. Rust cannot represent these (`u64`), and text is rejected as `NegativeAmount` or `InvalidAmount`.
6. **Empty and delimiter-bearing recipients or targets.** JS emits an empty field or a field containing `;` (send) or `,` (attestation), which the decoders misparse. Rust refuses with `EmptyField` or `ForbiddenByte`. Recipients and targets are capped at 90 bytes (`FieldTooLong`) as a defensive bound, not a JS rule.
7. **Commit channel longer than 42 bytes without a reference.** `encodeCommit` uses `params.ref || 0`, so a missing reference silently becomes `ref:0`, which redirects the commit. Rust requires `ChannelLocation::Reference(n)` explicitly and otherwise returns `ChannelAddressRequiresReference`. Reference 0 is emitted when explicitly requested, and that matches JS.
8. **Empty commit channel.** JS emits an empty field; Rust refuses (`EmptyField`).
9. **Clearlist id 0.** JS treats `0` as falsy and emits no clearlist field, which the decoder reads as no clearlist. Rust emits `0`, which the decoder reads as clearlist 0.
10. **Array clearlists.** JS emits `[7,11]`, which the decoder splits on comma before bracket parsing. The Rust type has no array form, so the row is `unrepresentable`. The decoder rejects the JS bytes with `BracketedListSplitBeforeParsing`, which the integration test checks.
11. **Sub-atomic commit input.** JS `0.000000001` tokens produces a fractional base36 amount (`0.3lll...m`). Rust takes integer atoms, so the row is `unrepresentable`.
12. **Framed commit body.** Property id 1065 is base36 `tl`, so the body begins `tl`. The crate decoder rejects any body that begins with `tl` (`NestedOrFramedBody`), while JS decodes it. Rust refuses with `AmbiguousFramedBody`.
13. **Boolean revoke.** JS writes a Boolean as `true`/`false`. The decoder reads only the literal `1` as revoke, so Boolean `true` becomes an issue, not a revoke. Rust takes `bool` and writes `1`/`0`. Numeric JS 0 and 1 are byte-identical.
14. **Comma in attestation metadata.** JS emits extra fields; the decoder keeps the first fragment only. Rust refuses with `ForbiddenByte`.
15. **Lowercase attestation metadata.** The decoder upper-cases metadata, so lowercase does not round-trip. Rust refuses with `MetadataNotUppercaseStable` rather than emitting bytes whose decoded value differs.
16. **Generic `Types.encodePayload` double prefix.** The wrapper writes `tl` plus the type, then appends an encoder result that already starts with `tl<type>`. This is the known legacy bug. Rust builders return only the single-prefix form.

## Withdrawal from channel: not implemented

The JS `encodeWithdrawal` writes three fields that the JS decoder does not read as intended:

- `withdrawAll: true` becomes the literal `true`. `decodeWithdrawal` checks for `1`, so `withdrawAll` decodes as `false`. A withdraw-all request silently becomes a partial withdrawal.
- The amount is written as decimal atoms (`100000000`), but `decodeWithdrawal` reads it as base36. One token decodes as about 28,211 tokens.
- `column` is written as `true`/`false`, but the decoder reads `1`.

No byte-identical output is possible for any nonzero amount, and the decodable form (base36 atoms, `1`/`0` flags) is a protocol decision, not a parity fix. This module therefore has no withdrawal builder. The divergence test checks that the crate's decoder reads the JS bytes as withdrawAll=false and a wrong amount. Implementing it needs an explicit decision about which bytes are canonical and whether chain history already uses the JS form.

## Round trips

- Simple send: `wire::parse_typed` (the crate's existing legacy typed parser) returns the original recipient, property id, and atoms, including the `~` form.
- Commit to channel and attestation: `legacy_txdecoder_audit::source_decode_body_unverified` (types 4 and 9) returns the original fields, with the metadata compared as decoded (upper-case).

## Limitations

- **Toolchain.** The pinned `1.90.0` could not be downloaded in this environment. Every check above used the local `nightly-2026-04-29` toolchain instead, so the results are not evidence for the pinned toolchain.
- **CI wiring.** `.github/workflows/ci.yml` does not run the new generator check. This PR adds the script and fixture but does not change CI.
- **Scope of parity.** The 18 `match` rows are fixed inputs. They do not cover the full JS input space, and JS number-precision behaviour outside these inputs is not modelled.
- **Not consensus.** These bytes are not validated against activation, sender authority, balances, or chain history.
- **Vendored dependency.** `fixtures/js_vendor/bignumber-9.1.2.js` is a third-party MIT JavaScript file used only by the generator. No Rust crate was added.
